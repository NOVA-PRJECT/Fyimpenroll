Database simplification and semester lifecycle implementation report

Prepared 26 October 2026. This report describes proposed implementation work based on the database inventory checked during this conversation and the current repository. It does not apply migrations, delete records, or change application behaviour.

Implementation is now present on `codex/semester-lifecycle-cleanup`. See `supabase/SEMESTER_LIFECYCLE_ROLLOUT.md` for delivered behaviour, verification and release limitations. Production is unchanged. The owner will run the reviewed `supabase/changes/semester_lifecycle.sql` file in the Supabase SQL Editor during release; no CLI installation or CLI migration registration is required for this workflow. The assistant supplies files for substantial database changes and does not execute them on the owner's behalf. The implementation uses term versions and four current-term read views, retains unscoped conflict diagnostics, and blocks active cross-campus class cleanup. Historical academic records remain in their base tables.

The intended outcome is a system that preserves academic history across semesters, clears temporary operational data, removes unwanted features and tracking tables, and exposes two distinct director actions: **Promote Students and Clear Temporary Semester Data** and **Delete Graduating Students**. Student registrations, timetable entries and teacher course assignments must survive promotion, including their concluded-term records. Promotion advances students in semesters 1–10 by one semester, including semester 10 to semester 11. Semester 11 identifies students who have completed the programme and await separate graduation deletion; it is not another teaching semester. Promotion must never invoke graduation deletion. Graduation deletion must not advance semesters or update the promotion cooldown. No separate completion field or distinguishing step is required.

The recommendations below preserve the existing 90-day promotion restriction. A waiting period prevents early repetition; it does not determine whether an academic semester has officially ended. The director still initiates the term transition.

The current implementation needs these changes:

| Area | Current behaviour found in the code | Required behaviour |
|---|---|---|
| Promotion | The backend promotes semesters 1–9, then automatically calls graduation cleanup for the original semester-10 students. | Promote semesters 1–10, including 10 to 11, and clear only the specified temporary records. Preserve registrations, timetable entries and teacher course assignments across terms. Keep semester-11 accounts until the separate deletion action; existing semester-11 students stay at 11. |
| Director screen | Promotion text says final-semester students will be permanently removed. Graduation controls mainly support failed cleanup retries. | Give promotion and graduation distinct controls, previews, confirmations, results and loading/error states. |
| Promotion retries | `promotion_receipts` stores a request key and original response. | Use a locked `campus_settings.last_promoted_at` check; refresh state after an ambiguous response. |
| Closed-term protection | Attendance services and SQL functions consult `retired_cohorts`. | Reject outdated requests using the current term boundary and shared transaction locking. |
| Graduation | API calls and database operations run in stages, recorded in two graduation tables. | Delete explicitly selected semester-11 student accounts and dependent rows in one separate database transaction. |
| Notices | Backend service, routes, mobile screens and student overview integration exist. | Remove the feature throughout the application. |
| Attendance unlocking | The old table remains, while current-semester correction no longer requires unlocking. | Remove the table and obsolete fields/dependencies while preserving teacher authorization and revision conflict checks. |

Six public tables are proposed for removal. The application would go from 26 to 20 public tables, assuming no additional table is introduced during implementation.

| Table to remove | Replacement or prerequisite |
|---|---|
| `period_unlock_requests` | No replacement table. Remove the obsolete unlock workflow and related dependencies. |
| `department_notices` | No replacement feature. Remove notices APIs, components, mobile routes and overview queries. |
| `retired_cohorts` | Replace its closed-term protection in both backend code and database write functions before dropping it. |
| `graduation_operations` | Replace staged deletion with a single graduation transaction and retain an ordinary audit event in `system_logs`. |
| `graduation_candidates` | Validate `students.current_semester = 11` and campus scope directly; no separate completion field or processing-stage records. |
| `promotion_receipts` | Use the settings row lock, cooldown check and timestamp update in the same promotion transaction. |

The remaining tables have three retention patterns: reusable master records, academic history that survives promotion, and temporary records whose concluded-term rows are deleted. A term ending is not grounds to delete all records associated with that term.

| Tables | Proposed retention |
|---|---|
| `campuses`, `departments`, `admins`, `faculty`, `students`, `courses`, `semester_blueprints`, `time_slots` | Keep reusable records. Promotion updates student semester values; the separate graduation action deletes eligible student accounts. |
| `campus_settings` | Keep. Store the promotion timestamp and authoritative current-term boundary here. Preserve settings that remain valid and explicitly close the outgoing registration window. |
| `student_registrations` | Keep all concluded-term registrations throughout the student's academic lifecycle, including course slots, total credits, selection snapshots and allocation metadata. Credit ledgers, semester reports and exports depend on this history. Promotion must not delete, reset or overwrite these records. |
| `registration_preferences` | Delete concluded-term ranked choices after allocation results and required snapshots are confirmed in retained student registrations. Keep the table for the next registration cycle; historical registration/ledger readers must not depend on preferences that will be removed. |
| `period_attendance`, `period_attendance_sessions` | Delete concluded-term marks and session summaries. Keep revision-based protection for new-term attendance. |
| `campus_sign_ins` | Delete sign-ins within the concluded campus term's date interval. These records have dates rather than an academic-year/semester identity. |
| `timetable_entries` | Keep concluded-term schedules and their course, teacher, campus, class, period and publication details. Show historical schedules through explicitly scoped history views; exclude them from current-term attendance and scheduling. Keep published-history protections. |
| `teacher_course_assignments` | Keep concluded-term teaching assignments, including their campus, academic year, semester and teacher/course links. Create separately scoped assignments for new terms rather than replacing historical assignments. |
| `timetable_conflicts` | Delete concluded-term generation diagnostics only where they are no longer needed and cleanup does not cascade into retained timetable entries, registrations or assignments. Preserve diagnostics still required by an active shared class. |
| `consent_records` | Keep for continuing users. Promotion is not a reason to request consent again. Existing account-deletion cascades remove the graduating user's records unless a different retention policy is explicitly selected. |
| `system_logs` | Retain promotion/graduation audit events. Clean completed operational job details under a separate retention rule; do not erase active worker state or the audit event for the cleanup itself. |
| `schema_migrations` | Keep. Database upgrade history must survive semester changes. |

Registration, credit-ledger, timetable and teaching-assignment history must remain readable across promotion. Historical readers must select the requested academic year, semester and campus/term rather than forcing the student's current semester or current campus settings onto every query. Preserve registered-credit totals and registration-time course snapshots even when the course catalogue changes. New-term upserts must use the complete term identity and must not overwrite prior-term rows.

Attendance marks, attendance-session summaries, campus sign-ins and preference submissions remain the temporary records proposed for deletion at term closure. Historical attendance percentages and attendance exports cannot be reconstructed from retained schedules alone; those screens must clearly report that the underlying attendance was cleared rather than present zero attendance as a measured result. If an attendance export is required, it must finish before deletion. Retained academic history remains in the database and does not depend on an external export.

Promotion should be implemented as one transaction in one database function. A series of independent Supabase `.delete()` calls from the backend does not provide the same rollback behaviour. PostgreSQL transactions group database changes into an all-or-nothing operation. [PostgreSQL transaction documentation](https://www.postgresql.org/docs/17/tutorial-transactions.html)

The promotion transaction should follow this sequence:

1. Validate the actor and resolve the campus from trusted authorization data. Keep the current campus-director scope.
2. Acquire the shared campus lifecycle lock and lock its `campus_settings` row. Promotion, graduation and term writes must follow a consistent lock order.
3. Check the authoritative `last_promoted_at` value using server time. Reject promotion within the existing 90-day interval. Compare the expected term boundary supplied by the client with the current one so a very old request cannot become valid just because 90 days elapsed.
4. Identify the outgoing student cohorts in semesters 1–10 and the temporary rows eligible for cleanup before changing their semester values. Explicitly exclude student registrations, timetable entries and teacher course assignments from deletion. Existing semester-11 students are awaiting deletion and must not be promoted again.
5. Block promotion while an outgoing allocation or timetable worker is queued/running, or explicitly cancel it under the same lifecycle protocol. A worker must not be able to commit old-term output after cleanup.
6. Validate shared-class dependencies and compute the exact outgoing-term deletion sets. Abort if another active campus would lose required data.
7. Remove scoped attendance marks and sessions, sign-ins, preferences and eligible concluded-term conflict diagnostics in dependency-safe order. Preserve all registrations, timetable entries and teacher course assignments, including concluded-term rows. Verify preference cleanup leaves the retained registration snapshots and credit ledger complete. Keep published-timetable protections intact; promotion must not bypass them to remove history.
8. Advance the original semester-1–10 students by one semester in a single scoped update. Semester 9 becomes 10 and semester 10 becomes 11. Keep all student profiles and Auth accounts; do not add a completion marker or delete graduates.
9. Leave existing semester-11 students at 11 and exclude them from new registration, allocation, timetable rosters, attendance and campus sign-ins while they await the separate deletion action. Never assign semester 12.
10. Close the registration window until it is explicitly configured for the next term. Apply an explicit academic-year rule: a semester transition does not always mean an academic-year change.
11. Set `last_promoted_at`, record the outgoing/incoming term boundary and insert the promotion audit event and row counts in `system_logs` inside the same transaction.
12. Commit once. Any error must roll back cleanup, semester changes, settings and the success audit record together.

After `promotion_receipts` is removed, an identical response is not guaranteed for a retried request. A simultaneous duplicate or immediate retry should be rejected as already promoted/locked, and the UI should reload campus settings and student counts. A network timeout is an unknown outcome until that state is refreshed; it is not proof of rollback. This simpler behaviour is the accepted tradeoff for removing the receipt table.

Removing `retired_cohorts` requires replacing its function, not only its queries. Reuse `last_promoted_at` as a term boundary where suitable, together with an initial-term fallback; alternatively use a small monotonically increasing current-term version on `campus_settings`. A version is optional, not a requirement for another table. The chosen identity must be carried by mutating requests and worker claims, and compared again inside the database transaction after acquiring the lifecycle lock. Attendance must still require an existing, published, current-term timetable entry and a date inside that term. Historical published entries and assignments will remain present, so existence or publication alone cannot establish that a class is active. Academic year and semester number alone are insufficient to identify every term transition. Store the necessary term identity on retained records where existing fields cannot distinguish repeated term instances.

The replacement checks must cover registration submissions and edits, manual allocations, allocation commits, timetable generation/publication, attendance submission, practical attendance copying and campus sign-ins. A request that began before promotion must either finish before cleanup or fail afterward. Replacing the backend check alone leaves SQL functions able to write stale data. Attendance revision checks remain necessary because two teachers can still edit the same current-term session concurrently.

The new **Delete Graduating Students** action should be a separate director screen or card. It should list semester-11 students with their admission number, name, department and current semester; support explicit selection; preview the exact count; and require a destructive-action confirmation. The normal semester-promotion confirmation must describe only promotion and temporary-record cleanup, explicitly state that registration and teaching history are preserved, and explain that semester-10 students move to 11 and remain in the system. Deleting graduates must not call promotion, clear other students' data, change `last_promoted_at` or be blocked by the promotion cooldown.

Graduation eligibility is represented by `students.current_semester = 11`. After promotion, former semester-9 students are in semester 10 and former semester-10 students are in semester 11, so the semester value already distinguishes them. No completion timestamp, separate confirmation of completion, or graduation tracking table is needed. The graduation function must recheck semester 11 and campus scope inside its transaction.

Change `students_current_semester_check` from the current 1–10 range to 1–11. Update student profile contracts, student-management validation, imports, filters and web/mobile displays to handle 11. Keep course, blueprint, registration, teaching-assignment and timetable semester ranges at 1–10: semester 11 is only the completed student state. Treat semester-11 accounts as awaiting deletion in the portal, without offering active-study actions. Ordinary student edits must not accidentally reset a completed student to an active semester or bypass the authorized promotion transition.

The old automatic deletion trigger for semesters above 10 was already removed by the October 25 cleanup migration. Keep it removed: reaching semester 11 must never delete an account automatically. For an older environment, apply that trigger retirement before allowing semester 11. At migration time, leave ordinary semester-10 students unchanged until an actual promotion. Reconcile any existing unfinished staged graduations individually, including Auth accounts whose student rows were already deleted; they cannot be discovered solely by querying current students in semester 11.

The graduation transaction should follow this sequence:

1. Validate the actor and selected UUIDs, deduplicate the IDs, and reject an empty or excessive batch using explicit API limits.
2. Acquire the same campus lifecycle lock used by promotion; lock the selected student/account rows in a consistent order. Concurrent promotion and graduation must not change the selection's meaning.
3. Recheck the entire selection against campus, student role and `current_semester = 11`. Reject a mixed invalid selection before any deletion, including any semester-10 student. Never permit an administrator or faculty account to be deleted through this function.
4. Check current Auth foreign keys, triggers and any Storage ownership. Keep external Storage-file cleanup outside the atomic database guarantee; if blocking objects exist, stop before deleting the batch and resolve them first.
5. Use a narrowly privileged database function to delete the selected `auth.users` rows and their verified dependent application rows in the same transaction. The repository already defines cascades from Auth users to students and from students to preferences, registrations, attendance marks and sign-ins; verify the deployed relationships before relying on them.
6. Insert one graduation audit event with the actor, campus, number deleted and an appropriate minimal identifier list. Do not retain a full duplicate student profile merely to replace the removed tracking tables.
7. Commit once. If one selected account cannot be deleted, roll back the selected batch. The UI must report this as a batch failure rather than partial success.

The registration preservation requirement applies throughout the student's academic lifecycle, including promotion from semester 10 to 11 and the period awaiting deletion. Under the separate full-account graduation-deletion design, that selected student's registrations are deleted only when their account is explicitly deleted; the confirmation must disclose this. Shared timetable entries and teacher course assignments must survive that action as institutional teaching history and must not be deleted merely because a participating student graduates. Any requirement to retain an individual student's credit ledger after full account deletion needs a separately defined alumni/archive policy; it is not implied by the semester cleanup action.

Direct Auth deletion needs verification against the managed Supabase schema and the database role executing the function. Supabase documents direct user deletion, cascading profile references, and Storage ownership constraints. Deletion does not retroactively invalidate already-issued access tokens, so verify that the backend continues to reject requests when the Auth identity or portal profile is gone. No Auth API call should be placed between database statements and described as part of the same SQL transaction. [Supabase user management](https://supabase.com/docs/guides/auth/managing-user-data)

The graduation button must handle lost responses by refreshing its selected-account state. If the whole selection is absent afterward, show that those accounts are already removed; if all remain, the action can be retried after revalidation. Do not weaken authorization by treating arbitrary unknown IDs as eligible graduates. Exactly reproducing the original deletion response would require retaining some request outcome; it is not necessary for safe deletion.

Published classes can include students from another campus, and timetable records have host-campus identity. Preserve shared schedules and teaching assignments across term transitions. Cleanup must not delete another campus's active student marks or attendance-session summaries just because one participating campus promotes. Determine the host and audience using the existing enrolment rules. The implementation must either coordinate term closure across the participating campuses or block destructive temporary-record cleanup until no active campus depends on those records. Unscoped deletion by course ID, semester number, or academic year is not acceptable.

Audit all current-term readers and schedule-generation constraints now that old timetables and assignments will remain. Historical teaching must not count as a current teacher clash, current workload, current enrolment or a reason that a new term is already published. Historical credit-ledger and export readers must continue to include the retained prior-term registrations. Apply the chosen current-term identity consistently in publication checks, uniqueness constraints, assignment mutations, roster calculations and UI filters; do not solve conflicts by deleting or rewriting previous-term rows.

The schema migration must replace dependent routines before dropping the six tables. Widen only the student current-semester constraint to 1–11, ensure the obsolete above-10 automatic deletion trigger remains absent, and keep academic course/registration constraints at 1–10. Replace `promote_campus_students_atomic` and its helper, `prepare_graduation`, `graduate_candidate_database`, `finish_graduation_candidate`, closed-attendance cleanup and any live callers. Promotion must increment only semesters 1–10; graduation deletion must require semester 11. Preserve all existing registrations, timetable entries and teacher course assignments during migration and promotion; backfill required term identity without losing historical values. Update `production_readiness()` to check the new lifecycle contract. Remove obsolete indexes, policies, grants and function signatures explicitly; use dependency checks rather than an unrestricted `DROP ... CASCADE`.

The old `period_attendance.is_late_entry` and `unlocked_by` fields can also be removed after confirming no current readers or writers depend on them. `campus_settings.timetable_constraints` and `registration_preferences.legacy_allocation_metadata_snapshot` are optional additional column cleanup, not prerequisites for this release. Scope them separately if preserving historical values is still useful.

Database access must remain backend-only. Any graduation function that needs elevated privileges must pin its search path, qualify referenced objects, enforce its campus/student eligibility contract, revoke public/anonymous/authenticated execution and grant execution only to the trusted backend role. Do not broadly grant the service role direct modification privileges across the Auth schema merely to make the new function work.

Verification must demonstrate behaviour, rather than merely assert that table names disappeared:

| Scenario | Required result |
|---|---|
| Normal promotion with semesters 1, 9, 10 and 11 | Semester 1 becomes 2; 9 becomes 10; 10 becomes 11; existing 11 remains 11. All student profiles and Auth accounts remain present. |
| Academic-history preservation across promotion | Every prior-term registration, timetable entry and teacher course assignment retains its identity and academic values. Registered credits, course snapshots and prior-term exports remain unchanged and readable. |
| New-term registration and teaching setup | New rows use the incoming term identity without overwriting earlier terms. Old published schedules and assignments do not create false current-term publication locks, clashes or workloads. |
| Preference and attendance cleanup | Only the scoped temporary records are deleted. Registration snapshots remain complete; cleared attendance is distinguished from a genuine zero-attendance result. |
| Semester bounds and automatic deletion | Student semester 11 is allowed; 12 is rejected. Academic course/registration semesters remain 1–10. Reaching 11 does not trigger account deletion. |
| Immediate duplicate or two concurrent promotions | Exactly one promotion succeeds; the other is rejected after acquiring the lock. |
| Failure halfway through promotion cleanup | All deletions, semester changes and timestamp changes roll back. |
| Semester-10 versus semester-11 graduation selection | Semester-10 students cannot be deleted through graduation; selected semester-11 students can. No separate completion field or step is used. |
| Semester-11 portal and write requests | Display completed/awaiting deletion status; reject new registrations, allocations, attendance, timetable roster participation and campus sign-ins. |
| Graduation batch with an invalid/cross-campus account | No account in the selection is deleted. |
| Separate graduation deletion and retained history | Registrations survive until explicit account deletion; deleting a selected graduate does not delete institutional timetable entries, teacher course assignments or another student's ledger. |
| Failure on a dependent account deletion | The whole selected batch remains intact. |
| Concurrent graduation, promotion and student import/update | Shared locking and eligibility checks preserve the intended cohort; newly created/advanced students are not accidentally deleted. |
| Attendance submission/copy or allocation worker overlaps promotion | It commits before cleanup or is rejected afterward; it cannot recreate concluded data. |
| Shared course/class across campuses | Active students elsewhere retain their required schedule and attendance. |
| Cleanup date boundaries | Outgoing sign-ins are removed using the campus term interval; new-term rows survive, including India-time date boundaries. |
| Deleted student's existing token | Backend rejects portal access after identity/profile deletion. |
| Lost response after either action | UI refresh distinguishes committed state from an operation that did not complete. |
| Notices removal | Student overview, HOD/teacher navigation and mobile/web builds work with no notices table or API. |
| Fresh database bootstrap | Historical baseline plus new migrations restore successfully, readiness passes, and backend-only grants remain correct. |

Run the repository checks after implementation: `npm test`, `npm run build:frontend`, `npm run typecheck --workspace=mobile`, and the documented mobile export/build with its required public environment values. Extend the existing database/service regression tests for the cases above. The current PGlite tests create only a minimal placeholder `auth.users` table; they cannot prove real Supabase Auth/session cascades, Storage constraints or hosted database privileges. The release should be staged as follows:

1. Implement and review the replacement functions, API changes, both independent UI actions, and tests locally. Supply the owner with the reviewed SQL file and execution instructions for substantial database changes; the owner executes it. Do not rewrite already-applied migration history.
2. Reconcile existing unfinished graduation records, including account-only remnants from partial deletion, before removing staged tracking. Leave ordinary semester-10 students at 10 until a real promotion moves them to 11. No initial completion marker or blanket conversion of semester-10 students is needed.
3. Produce a recovery backup covering application and Auth data, and Storage where relevant. A public-schema JSON export alone cannot restore deleted login credentials and identities. Rehearse the exact upgrade and recovery process in isolation.
4. Deploy with writes paused or use an explicitly compatible transitional release. Drain old workers and ensure old backend instances cannot continue calling removed routines. Coordinate mobile clients that still contain notices or old promotion contracts.
5. Apply the migration, verify table/routine inventory, grants and readiness, and compare retained registration, timetable and assignment records with the recovery snapshot. Then deploy/activate matching backend and client changes and smoke-test both actions, historical ledgers and new-term scheduling using synthetic data in staging.
6. Reopen production writes after verification. The schema release itself must not automatically promote students, clear a semester, or delete graduates; those are later, separately initiated director actions.

For implementation, the agreed direction is: remove all six listed tables; retain the 90-day timestamp guard; perform promotion of semesters 1–10 plus scoped temporary-record cleanup in one transaction; preserve concluded-term student registrations, timetable entries and teacher course assignments; keep the credit ledger and historical teaching reports available across terms; use semester 11 for completed students awaiting deletion; perform selected semester-11 graduation deletion in a different transaction behind its own button; add no separate completion field or distinguishing step; and retain ordinary audit events. Attendance, sign-ins and ranked preference submissions remain temporary records under this plan. The academic-year transition rule, shared-campus term coordination and any required pre-deletion attendance export need explicit definitions before the destructive functions are finalized. These are behaviour decisions, not reasons to introduce more tracking tables automatically.
