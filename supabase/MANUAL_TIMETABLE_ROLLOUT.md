# Manual timetable fallback

The feature is available to a campus director after the latest generation attempt fails or produces an incomplete review draft. Registrations must be closed. It starts from the partial draft, the previous saved draft, or an empty schedule. A new generation attempt supersedes the previous manual draft. Published schedules remain locked.

The editor supports placing, moving and removing sessions, linked parallel baskets, undo, remaining hours, validation previews and saved drafts. “Follow rules” permits incomplete drafts but rejects scheduling violations and requires full validity for publication. “Allow rule overrides” requires a reason and permits publication with recorded scheduling violations or missing hours after explicit acknowledgement. Empty schedules, duplicate course/slot identities, invalid slots, foreign cohorts and stale terms cannot be overridden. Teacher-course mutations, including substitutions, are exclusively HOD operations; the director cannot supply a teacher through the scheduling API.

Before deploying the matching backend/frontend, the database owner runs [changes/manual_timetable.sql](changes/manual_timetable.sql) once in the SQL Editor, after the already applied semester lifecycle SQL. Do not rerun `semester_lifecycle.sql` on the existing project. The assistant leaves substantial SQL execution to the owner, following this repository’s existing release workflow. The new SQL is also included in fresh-project bootstrap. It introduces no new tables and does not migrate existing timetable or assignment records.

Manual drafts and their effective generation rules are stored in the latest timetable job’s metadata. Every save/publication creates an audit event containing the director, mode, reason, complete draft, validation results and previous revision. Publication records its timestamp, actor and session count. The normal timetable screen retains the recorded violations and missing-hours warning after publication. Older failed jobs without a rule snapshot use the repository’s effective rules.

The backend performs validation against current registrations, course hours, parallel groups and HOD assignments. Database commits recheck a fingerprint of enrollment, course metadata, assignments, slots, occupancy, settings and the job under the existing lifecycle/teacher advisory lock. Changed inputs require reloading the editor. Publication atomically replaces draft sessions with HOD-derived teachers and publishes every saved entry, or rolls back in full. Override publication bypasses only the teacher-clash part of the teacher trigger within that transaction; teacher identity, term, cohort, publication locks and permissions remain enforced. The override setting is restored before returning.

Verify locally with `npm test` and `npm run build:frontend`. Focused coverage lives in `tests/manual-timetable.test.cjs` and `frontend/tests/manual-timetable.test.cjs`. After deployment, verify using a failed or partial generation cohort: strict-mode rejection, synchronized parallel moves, override reason/acknowledgement, stale-editor reload, read-only teacher assignments and published placement locks. Check permissions with a director, HOD and another-campus account. Hosted multi-connection concurrency and authenticated browser flows require staging accounts; local tests use an isolated PostgreSQL runtime and synthetic records.

Recovery: retain the feature SQL and the audit records. Reverting application code does not unpublish or remove manual schedules. Deploy forward fixes for published data; never delete published entries or replay the bootstrap to undo this feature.
