# Production and complexity audit

Date: 10 October 2026. Scope: backend modules and request guards, web screens/session handling, mobile contracts/offline queue, SQL schema/migrations, solver jobs, exports, workspace dependencies and deployment configuration. Application code and database state were not changed by this audit. New files contain this review and isolated reproductions.

## Assessment

The modular NestJS backend, Next.js frontend, Supabase database and local OR-Tools solver are a reasonable architecture for this portal. My recommendation is to keep that structure and make targeted repairs. The codebase does contain unnecessary duplication and large components, but its size alone does not justify a rewrite.

**I would not certify the current repository as production-ready or say no optimizations remain.** Several correctness, security and recovery issues are more important than cosmetic cleanup. The earlier passing build/test gate establishes the paths it exercised; this audit reproduced additional gaps.

The inventory contains approximately 16,461 nonblank backend source lines across 97 TS/Python files, 20,392 frontend source lines across 58 TS/TSX files, 5,026 mobile lines across 53 files, and 5,921 migration lines across 38 SQL files. Counts exclude dependencies/generated builds and exclude backend `.spec.ts` files. They are size measurements, not complexity scores. CSS, tests and documentation add files but do not imply equivalent runtime complexity. Two ignored `.release-clean-*` directories and dependency/build folders contribute to local disk use; no disk-size or bundle-size savings are claimed here.

## Useful simplifications and smaller optimizations

These changes should follow the correctness repairs and preserve existing behavior. None require another broad architecture layer.

1. **Split a few large files along existing responsibilities.** The director timetable page, BlueprintTab, TeacherAssignmentTab, registration screen and allocation/registration/attendance services contain roughly 1,300–2,150 nonblank lines each. Extract export actions, editing forms, job-status UI, query loaders and pure allocation decisions. Keep orchestration visible; avoid a mass refactor or arbitrary file-length target.
2. **Consolidate duplicate contracts and workflows.** Backend/frontend course types and rule constants are duplicated; role drift is already proven in mobile. Generate/share the small set of stable API contracts. Maintain a single authority for enrollment/credit calculation and export output. Converge normal student/shared password-change and reset synchronization around one tested server contract while preserving the recovery-link entry point.
3. **Load heavy frontend tools when used.** HOD imports all tabs eagerly, including the React Flow assignment editor; the timetable page statically imports ExcelJS. Use conditional dynamic imports for those tabs/libraries or canonical backend download endpoints. Next documents the [supported lazy-loading approach](https://nextjs.org/docs/app/guides/lazy-loading). Measure route JavaScript and loading time before claiming savings.
4. **Replace repeated linear roster lookups with a Map.** `campus-attendance.service.ts:449` and `:452` scan the sign-in array twice for every student. Index once by student/session so the merge becomes linear in the combined dataset. This is a small, directly useful optimization.
5. **Bound reporting work by the real operation.** New exports collect rows and workbooks in memory; attendance traversal has a 100,000-record safety ceiling. A full-term department report can reach that ceiling even when the student count is modest. Filter by term/department early, aggregate attendance counts in SQL or stream larger outputs, and bound concurrent exports. Do not merely raise the cap without a measured memory/latency budget.
6. **Review two duplicate indexes.** The explicit `(timetable_slot_id, attendance_date)` session index duplicates the identical UNIQUE constraint's index; the retired-cohort lookup similarly duplicates `(campus_id, academic_year, semester)`. Inspect deployed definitions, constraints and query plans before a forward index-removal migration. Do not remove a UNIQUE constraint to save storage.
7. **Remove dead compatibility code after confirming schema rollout.** There are mock-specific runtime branches, old six-slot fallbacks, legacy logging-view retries, and an AI-generator/prompt path outside the active OR-Tools pipeline. Verify call sites, supported databases and remaining tests before removing unused paths. Migrations and intentional `system_logs` views are history/contracts, not dead code to delete.
8. **Reduce avoidable rerenders and polling work.** `useCurrentTime` updates entire large director/registration pages every second. Isolate the countdown/cooldown display, or use the smallest interval the UX requires without freezing deadline decisions. Poll job status only while active and prefer compact fields over `select('*')` when the UI needs few fields.
9. **Trim deployment installation scope after testing it.** Both providers install the whole monorepo; Render also retains all dev dependencies. The Expo toolchain is not needed to run the backend. Validate selected-workspace install/build or a separate runtime artifact against the root lockfile and keep mobile as a workspace; do not delete mobile or reintroduce React-resolution workarounds.
10. **Finish the remaining lint/operational checks.** Current frontend lint has zero errors and 40 warnings, including effect dependencies and unused state. Review dependency warnings for stale data rather than automatically adding everything to arrays. Health currently reports process uptime only. Add distinct readiness/dependency diagnostics and request/job correlation; require migration, browser and load checks in CI/staging for the critical paths. Avoid making every health probe a costly database/Auth round trip.

## Database and workflow complexity

The database needs transactions, constraints, scopes, delivery identity and recoverable operation state; removing those to make the system appear smaller would reintroduce defects. The excess complexity is mainly multiple generations of contracts and duplicated consumers. Keep applied migrations immutable. Provide one supported installation/migration baseline and verify it against an empty staging database, then compare deployed privileges/FKs/indexes to that baseline. Existing `MIGRATIONS.md` is an inventory, not proof that all historical migrations can be replayed safely. No new tables or a second job/enrollment store are recommended just for this review.

It calls actual compiled AuthService/AuthGuard/FacultyService; transpiles the actual frontend workbook helper and mobile profile schema; executes the actual draft RPC in PGlite; uses the actual constraint-file store. This includes mobile/build-tool transitive dependencies declared in production graphs and propagated severity; it is not 42 confirmed reachable exploits. Some proposed automatic fixes are major downgrades. Do not run `npm audit fix --force` indiscriminately.
- Mobile TypeScript was checked with `npm exec --offline --workspace=mobile -- tsc --noEmit --incremental false`; results are in `mobile-audit-typecheck.log`. No mobile device/browser release flow was exercised.
- The earlier web/backend gate passed 224 backend tests, 5 frontend module tests, lint with 0 errors/40 warnings after final cleanup, and clean root/frontend builds. Those evidence logs remain valid for their tested scope. No full rebuild was necessary for this review because application source was unchanged.
- No live Supabase grants/schema/data, actual Render/Vercel settings, PostgreSQL two-connection races, HTTP load/latency, deployed memory usage, browser bundle sizes, mobile device flows or backup restoration were inspected. Therefore this is a repository audit, not a production certification or a guarantee that every possible defect has been found.

## Recommended order

First update/triage dependencies and repair publication/fencing, exact roster identity and durable storage. Then repair session failure/cache handling, the live HOD export, complete-data loading and mobile contracts if shipping mobile. Finally apply the smaller simplifications with measurements. Fixing these concrete paths should make the code easier to maintain; a rewrite, more microservices or additional generic frameworks is not justified by the inspected source.
